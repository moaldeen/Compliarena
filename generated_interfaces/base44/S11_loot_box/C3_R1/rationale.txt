Q2 — Contextual & Information Tracking The Application Information shaped the design in these direct ways: "real-money in-app purchase transactions converted into in-game Gems" → The gem balance is displayed prominently and decremented visibly upon purchase. The price is shown in Gems (not real currency), and the confirmation dialog restates the gem cost, because the player's mental model is in Gems — the real-money conversion happened upstream. "resolved server-side using a randomized reward resolution system" → The compliance footer explicitly states outcomes are "determined server-side." The client rollReward function simulates the server response with a delay (1.2s opening animation) so the UI demonstrates the round-trip without implying client-side resolution. "four rarity tiers" and "tier-weighted outcome logic" → Exactly four reward cards are shown, each with a visible percentage that sums to 100% (60 + 25 + 12 + 3). The drop rates are not hidden — they're printed on each card as a permanent label, not behind a tap. "stored in the player's remote inventory" → The COLLECT action closes the reveal loop; the implication is that the item has been persisted server-side. No local "inventory" UI was added because the brief scoped this screen to the purchase popup only. "Apple App Store Guideline 3.1.1 and Google Play loot box disclosure policy" → This is the single most influential parameter. It is the reason the odds are permanently visible on each card, the reason the footer states the disclosure explicitly, and the reason no odds are hidden behind an accordion or tooltip. "landscape 16:9" and "not a vertical phone app" → The DeviceFrame uses aspect-video (16:9) with a landscape orientation. All content is laid out horizontally (chest left, cards right) rather than the vertical stacking typical of mobile portrait F2P UIs. "Do not make it look like a casino" → I avoided slot-machine imagery, spinning reels, or gold-coin shower animations. The reveal is a soft burst of light rays, not a jackpot effect. What I did not alter based on the manifest: The network pipeline details ("transmits purchase requests to an in-app billing service") did not change the UI layout because that is a backend concern — the player sees a unified purchase flow regardless of the underlying billing transport. I did not add a "processing payment" spinner distinct from the "Opening…" state because, from the player's perspective, the chest-opening animation is the processing state. Adding a separate billing loader wouldexpose implementation detail that belongs behind the abstraction. Q3 — Design Intent & Interaction Trade-offs Core goals, in priority order: Regulatory compliance without UX harm — The odds must be visible before purchase, but displaying them shouldn't make the screen feel like a terms-of-service page. I solved this by making the drop rate a small, permanent label on each card rather than a separate disclosure panel. The information is present but not dominant. Friction where it matters, none where it doesn't — The two-step buy → confirm flow adds intentional friction before a real-money conversion. But once the player confirms, the opening animation and reveal flow are seamless — no extra "are you sure you want to open it?" prompts. Visual hierarchy that drives the purchase — The chest is the largest, brightest element. The BUY NOW button is the only green CTA. Everything else (cards, odds, footer) is supporting context at lower visual weight. Key trade-offs: Information density vs. readability: Four cards with name + rarity + percentage in a 16:9 frame is tight. I chose to compress card padding and use very small font sizes (7–10px) rather than reduce the number of visible fields, because removing any of the three card labels (name, rarity, odds) would either violate the disclosure policy or reduce player comprehension. Compliance footer vs. space: The footer line is 7–8px — barely readable but present. I kept it because the explicit disclosure language ("Drop rates shown above. Each purchase yields exactly one item. Outcomes determined server-side.") provides legalcoverage that the card labels alone may not. If space became critical, this footer is the first element I would shorten, not the card data. Animation richness vs. frame-fit constraint: I used framer-motion for the chest glow, sparkles, opening shake, and reward reveal — but kept each animation compact enough that nothing overflows the device frame. The burst-ray effect on reveal is centered and pointer-events-none so it never interferes with the COLLECT button. Confirmation dialog vs. flow speed: A two-step confirmation adds ~2 seconds to the purchase path. I accepted this trade-off because real-money conversions are irreversible, and the cost of an accidental tap (a chargeback or refund request) is higher than the cost of one extra tap. Disabled vs. hidden BUY button: When the player can't afford the chest, I disable the button rather than hiding it. Showing the disabled state teaches the player the price and the gem deficit, which is more informative than removing the button entirely — but I grey it out rather than showing an aggressive "BUY MORE GEMS" upsell, because the brief scoped this screen to the chest popup only.
