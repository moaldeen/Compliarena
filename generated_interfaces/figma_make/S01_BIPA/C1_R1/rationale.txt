Q1 — Structural Elements & Defaults The screen is organized as a single scrollable-free card inside a phone frame, top-to-bottom: status bar → bank header → white content card. The content card has three logical zones: identity inputs, biometric toggles, and action buttons. Mandatory elements: Email field (pre-filled as a returning user signal — not blank, because this is a setup screen, not first registration) Password field with show/hide toggle — required by the brief as the "traditional" path At least one CTA button — the system must always have an escape route via password Optional / conditional elements: The biometric login button only appears when a toggle is enabled — it would be misleading to show a "Log in with Face ID" button before the user has opted in "Forgot password?" is included because omitting it on a security screen creates a dead end; it costs nothing spatially The footer encryption note is low-priority copy, rendered small — present for trust signaling, not interaction Default states: Both biometric toggles default to off — biometrics are an opt-in capability, not assumed. Defaulting them on would imply consent without action, which is a privacy concern Password button is visually demoted (gray) when a biometric is enabled — the hierarchy shifts to reflect the user's chosen preference, but the fallback remains accessible Q2 — Contextual & Manifest Tracking The manifest established two facts: Mobile Banking Application and biometric data is collected and shared with verification network APIs. How each shaped the UI: Manifest value Design response Mobile Banking Fixed 375×720 phone frame, touch-sized tap targets (min 36px), no hover-dependent interactions Biometric collection Toggles are explicit opt-in controls, not silent background enrollment — the user makes a conscious choice per method Shared to verification network The architectural constraint explicitly said do not surface backend telemetry in the UI, so no API status, sync indicators, or network labels appear What was deliberately excluded: The manifest mentions a verification network, which might suggest showing connection status or a sync badge. This was excluded. The constraint forbids it, and more practically, surfacing infrastructure state on an auth screen adds cognitive noise at the most sensitive moment in the user journey. The encryption footer note ("256-bit") addresses the underlying trust need without exposing backend specifics. Q3 — Design Intent & Interaction Balance Three core trade-offs were prioritized: 1. Progressive disclosure over front-loading Rather than presenting every option at once (password form + two biometric prompts + a scan flow all visible), the screen uses a three-state flow: form → scan → confirmation. Each state has one clear job. This reduces the number of decisions a user must make simultaneously without hiding any capability. 2. Mutual exclusivity of biometrics Enabling Face ID disables Fingerprint and vice versa. This is a deliberate constraint. Allowing both simultaneously creates ambiguity at login time — which method takes priority? The toggle pattern enforces a single registered method, which maps to how device-level biometric APIs actually work, and prevents user confusion on subsequent logins. 3. Hierarchy-as-confirmation of user intent When a biometric toggle is enabled, the biometric CTA moves to primary position (gradient, elevated shadow) and the password button drops to secondary styling (flat gray). This visual demotion isn't hiding the password option — it's reflecting the user's stated preference back at them, reducing the chance they default to password when they intended to use biometrics. The password button remains fully functional and labeled; it's just not competing for equal attention anymore. The tension being managed throughout is security thoroughness vs. interaction speed — the screen must communicate that real choices with real consequences are being made, while not burying a returning user in friction every time they open the app
