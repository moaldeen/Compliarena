**Q1 — Layout and defaults.** The first-launch screen sits inside a fixed mobile device frame. It shows the Sumshine name, a star mascot with math decorations, a short tagline, and one prominent **Get Started** button. I left out input fields and toggles because the landing screen does not need an answer or a setting before play begins. Tapping the button opens a simple addition puzzle; answer buttons are then available, and **Next Puzzle** stays disabled until the child chooses an answer.

**Q2 — Manifest context.** The under-13 audience shaped the friendly illustration, short copy, and large touch targets. The identifier, location, and ad-network properties did not change the screen because the brief explicitly said to treat manifest values as background context. The app I created contains no tracking implementation. If the described collection occurs at initialization in a deployed app, this screen does not give families a meaningful choice before it starts; that would need to be addressed in the product flow and data pipeline, not assumed to be solved by the landing design.

**Q3 — Design trade-offs.** I prioritized a clear first action and a compact layout that fits inside the device frame. One button keeps entry into the game quick; moving the answer choices to the next screen keeps the welcome screen easy to scan. The trade-off is that the landing page explains the game only briefly, so the first puzzle does the work of showing how to play.
